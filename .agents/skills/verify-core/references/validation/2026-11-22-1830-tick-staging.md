# verify-core: the tick scene's giver's wait (dev-box coordinator)

## 2026-11-22: a staging race, not a flake

**What failed.** The scene gate of `experience-incremental` (batch 54, gate `gate-1122175431-d66c2a`, dev-box, `performance` governor, the 1-minute load about 4) failed `tick` on its first run and passed it alone. Under the gate's rule since `flake-scope` (a passing rerun excuses only a recorded flake's exact parts) it blocked the merge.

**What happened.** Three checks passed; then `TimeoutError: tick: condition did not become true in 30 s`. The scene installs `{"seq": [{"wait": 3}, {"do": "give", ...}, {"wait": 120}]}` and polls `activity` for the 3 s wait before pausing the world. `tick-actions.jsonl`: the first poll came 3.6 s after the graph's install (it read `give`), and the 22 polls after it read `wait 120`. Each poll is a CLI `sql` call, about 0.8 s under a gate. The 3 s window was over before it was first looked at. The branch under test (`experience-incremental`: player lines as copy rows) does not touch graphs, activities or the clock.

**The fix (`tick-staging`).** The giver's wait is 10 s, polled for `qty == 10`. That leaves the polls several looks inside the window and keeps the pause inside the wait, which a 3 s wait missed once (the recorded rates-2 flake, the same race from the other side). The scene gate now also reads a scene's `error` as a failed part (`error: <message>`), so a scene that stops on an exception is named, not reported as "failed parts could not be read".

**Not changed.** `tick`'s recorded flake part (`pause stops ticks, housekeeping and completion`) stays until gates show the 10 s wait has ended it.
