# doing-renew: a continuous activity renewed in place (verify-core)

Branch `doing-renew` on main `3df6e1f1` (frame-views merged), code commit `b1874726`. The first runs were on the branch before its rebase, which was main `7d627e75` plus the change; the authority's only difference between `7d627e75` and `633dfbf1` was none. Server: the worker's own `slop-doingrenew-stdb` (`clockworklabs/spacetime:v2.14.1`, 127.0.0.1:3441), so no battle lock was taken. No mind service ran, there were no model calls, and the host was shared (load 5–20).

## The change

The fault: when a rest finished, the woken evaluation in that same tick read the leaf's success once (`finished`) and the pass ended with nothing running. The rest began again at the body's slot evaluation, up to a second later (in fact about 1 s: an 8 s rest ends at its own slot's phase, and the slot is skipped in that tick since the body was already evaluated). The `doing` row was deleted at the end and inserted at the next start.

Now `brain.rs` `renew`: after a pass that came to `Ok` with nothing under way, having read a leaf's success, a second pass runs in which only that leaf may begin. Any other leaf, a `say`, a `think` or a finished plan ends the pass as "running", and it is undone (the mind state, path, status and running leaf are restored). It applies only to a continuous act card (`town::continuous`: not `record`, `aside` or `turn`; rest, sleep, work, eat, play). It never applies to a played body, never when the root is a `seq` (the plan finished), and only under the new law `renew_in_place` (on). `town::shown` keeps `since_ms` when the same skill, target, `indoors` and spot (within 0.5 m) is shown again in the transaction that ended it (`ENDED`, thread-local, cleared per transaction).

SpacetimeDB check: a delete and an insert of one primary key in one transaction are one update to subscribers. The docs say each transaction sends zero or one update holding the set of inserted and deleted rows (https://spacetimedb.com/docs/clients/subscriptions/semantics), and that a same-key `update()` is an update event (https://spacetimedb.com/docs/tables/constraints). The 2.14.1 SDK pairs deletes and inserts by primary key into updates (`spacetimedb-sdk-2.14.1/src/client_cache.rs` `derive_updates`). The module's own `try_insert_or_update` is a `delete` then an `insert` (`spacetimedb-2.14.1/src/table.rs`). The docs do not cover a same-key delete and insert inside one reducer; that is verified from versioned source. The renewal needs no schema change (no column, no table).

- **Blinks by skill.** A blink is a row deleted and inserted again within 1.5 s.
  - Cullet, same-skill blinks per minute: main had gather 48, keep 24, make 4, play 5 and face 25; the branch had gather 2, play 4, sleep 2 and face 35.
  - The rest on the branch are a different activity in between: a turn (`face`), a walk between two plays or two bushes, or a sleep broken off by a turn and taken up at the next evaluation.
  - In the battle world: main had gather 838 and plant 20; the branch had gather 138. Fighting moves have no act card, so the battle's own fighters add nothing to `doing`; these rows are the realm's residents.
- **Row operations.** Subscribers get fewer separate changes and far fewer "doing nothing" gaps. Raw row operations on the wire are about the same or a little higher, for two reasons: an update travels as a delete and an insert in one transaction, and work repeats faster.
- **Pacing (a side effect).** Gather starts per gatherer-minute: realm-4 13.5 → 15.1 (+12%), Cullet 4.7 → 5.3 (+13%). The idle second between two gathers is gone. Trials comparing across this change should note `renew_in_place`.
- **The player in Cullet** (busiest spot, 6 seen): main `seen_doing_near` 2 updates, 3 deletes, 1 insert, with 18 cues of nothing per minute; the branch 0 updates, 3 deletes, 2 inserts, with 18 cues of nothing per minute. Both are dominated by turns, and the scene seen is small. verify-player `rest_seen.py` measures the resting case directly.

## Not covered

- Performance at scale: only the one 20 s `bench.py` pair above (about 190 residents, no players). The extra pass (`brain.renew` detail span) runs only after a continuous leaf finished well. No 216-character or battle profile was taken.
- Played bodies are excluded by design; a person's own repeated command is not renewed.
- The `seq` root is excluded (the "I finished my plan" deliberation keeps firing). A routine whose rest sits inside a `seq` at a lower level still renews only when the pass ends `Ok`, not mid-sequence.
- `doing_cost`, `fights` and the long scenes were not run.
