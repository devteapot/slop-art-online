# Belief-based point navigation

Branch `nav-planner` from `0ea97a1d`. Spark, `slop-move-stdb` on loopback port 3361, SpacetimeDB 2.14.1. The run uses scripted drivers and no mind service or model calls. `nav_belief` defaults to false.

## Implementation

Each chunk is labelled lazily by four-connected passable components over the actor's belief. The coarse graph connects two components only when their labels meet on a passable shared boundary. Every selected region therefore has a reachable boundary crossing from the preceding region. Unknown tiles remain traversable at the configured unknown cost. The finer search uses the same costs and disallows diagonal corner cutting. Coarse and tile searches keep their queues, costs and parents during pauses, with at most 512 heap pops per steering update, including at most 32 coarse pops. The 40,000-pop total limit is distinct from an empty frontier. A change of goal, start pose, observed ground or gates, or route costs invalidates a paused search. A missing cache is rebuilt from the persisted goal and current pose.

Buffered observations are visible to planning at once. Persistence drains one dirty block per actor every 5.5 seconds, oldest first, with a maximum sustained rate of about 0.182 rows per actor-second. A window shorter than several writes can still include one extra write across its starting boundary. The existing cadence of observation determines when the next eligible block is written. The queue retains dirty blocks until written or the actor dies. A module reload can lose unflushed observations, as with the previous buffer. Under continuous exploration, persistence lag depends on the rate at which distinct blocks are dirtied. The snapshots used for scoring and fuel contain persisted observations and can be behind the planner.

This follows the existing SpacetimeDB indexes: `known_ground` reads use `by_actor_block`, terrain edits use `chunk`, and remembered gates use `observer`. Flush writes at most one row through its primary key or inserts one block. Search state is an in-module cache. The design uses the existing schema, subscriptions, and visibility. Private route-exit diagnostics log actor, authority timestamp, and terminal reason.
