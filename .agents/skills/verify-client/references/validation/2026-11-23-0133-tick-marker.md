# The step marker (`tick-marker`): the client surface

Validated on the dev-box on branch `tick-marker` (from `origin/main` `afe588401`; module from `3d20f889c`). Server `mc-stdb` (private, `127.0.0.1:3390`, v2.14.1); `performance` governor. No paid model calls.

**The change.** `tick-marker` adds:
- the `tick_marker_on` law (value-only, Delivery, off by default);
- the private one-row `tick_mark` table, which each tick writes while the law holds;
- the watcher option, `gate-load watch` `"marker": true`.

The bindings were regenerated with `living/tools/generate_bindings.sh` (the pinned v2.14.1 image): `tick_mark_table.rs`, `tick_mark_type.rs` and `mod.rs`, not edited by hand.

**Scoped `maintain-verification-skill` pass.** A new private table is a shape change:
- `drive.py` `PRIVATE` names `tick_mark`;
- a new check, `scripts/tick_marker.py`, which `run.py` runs last;
- `features/visibility.md` and the map's row (`features/README.md`).

## Run `client-tm-1123-0227` (default seed, scoped build)

- **`drive.py`:** 45 PASS, no FAIL. The source inventory matches `PRIVATE`, `tick_mark` included. An anonymous connection's subscription to `tick_mark` is refused ("no such table … may be marked private"; `private-tick_mark.json`, `visibility.json`).
- **`cues.py`:** 23 PASS, no FAIL.
- **`tick_marker.py`,** run three times on the same world:
  1. **First run:** 4 of 5. The world was fresh, and "off: no tick writes `tick_mark`" passed with no row. The "on" check failed on the script: it read the row and then `clock` in two SQL calls about 0.3 s apart, so the counts differed by about 19 ticks, against a tolerance of 2.
  2. **Fixed check:** the row's count must lie between two reads of `clock` around it. The second run, on the same world, failed "off": the row the first run left still holds a tick no tick moves, and the check expected none.
  3. **Corrected "off" check:** no row, or one whose tick stays while `clock` moves. Third run: **5 of 5.**
     - off, nothing written (the earlier row stays at tick 15000 while `clock` runs on);
     - on, each read's count between `clock`'s around it, moving on with it;
     - 16.67 ms a tick on average from `start_us`;
     - anonymous SQL refused ("no such table: `tick_mark`");
     - off again, the row stops at tick 16497 while `clock` runs on.

   Together the first and third runs cover "off" on a fresh world and on a used one.

**Cleanup.** The world was deleted and SQL answers 404. Evidence is in `.local/living/verify/client-tm-1123-0227/`.
