# Game client on a land world

**Perception (docs/PERCEPTION.md).** The client reads only what its character perceives: the per-sender `seen_*` views for others and the `my_*` views for its own state, which a default (`scoped`) build makes the only way in. The other subscriptions are public world data by chunk window. The former `docs/perception-client.patch` landed on 2026-11-09 and was deleted.

## Sub-features

- The game client (`living/game`) subscribes in stages (`living/game/src/net.rs`, module comment):
  1. `cover_law`, `world`, `land` and `settlement` whole (`cover_law` since cover-sight, 2026-11-18; 1, 1 and about 8 rows for the other three).
  2. For the connection's lifetime, 33 queries with no window and no join: the 23 of `PERCEIVED` (since battle-views-client, 2026-11-20, without `seen_characters`, which is in the perception set below: `my_body`, `my_fighter`, `my_doing` (since 2026-11-10, `scale-1`: the own rows, out of `seen_*`), `my_characters`, `my_vitals`, `my_places`, `my_inventory`, `my_know_how`, `my_combat`, `my_readiness`, `my_offers`, `my_known_names`, `my_earshot`, `speech_card`, `my_records`, `heard_sounds`, `my_senses`, `my_act_outcomes`, `skill_card`, `act_card`, `weather` and, since 2026-11-10, `script WHERE name = 'skills'`: the installed skill script, about 70 kB once, again only on an install; `verbs.rs` compiles it to offer acts; and, since law-override-client (2026-11-19), `law_override`, the world's own law values, tens of rows: `verbs::Rules` compiles the script with them (`Scripts::with_overrides`) and, when only the rows change at the same revision, lays them over in place (`apply_overrides`: a value-only law, no compile), before `perception_law` reads a law each frame (`verbs::refresh_rules` in `Phase::Net`); in one set with `script`, so a reconnect's first result holds both, and the base being applied re-reads the rows; [verify-ui law-override.md](../../verify-ui/features/law-override.md)) and, since frame-views (2026-11-19), the perception streams as a subscription set of their own, chosen by the world's two delivery laws once the client has compiled the installed script with the overrides (`net::perception_law`, again whenever the laws in force change: `Rules::laws_key`, a compile or an in-place value-only edit): while `cue_transport_on` and `near_tier_on` are both off, the 3 of `UNTIERED_STREAMS`, `seen_bodies`, `seen_fighters` and `seen_doing`, so the client's queries are exactly main's (27 plus `gate` or `terrain_chunk`; main has the three in its base set); either on, the 9 of `TIERED_STREAMS`: each stream's near and far tier (`seen_bodies_near`/`_far`, `seen_fighters_near`/`_far`, `seen_doing_near`/`_far`) and its cue event table (`seen_body_cue`, `seen_fighter_cue`, `seen_doing_cue`; row-level security gives each connection only its own). Since battle-views-client (2026-11-20, docs/BATTLE_VIEWERS.md "Rollout") the set is a `net::Feed` of three choices, all made in `perception_law`: the tier state above, `motion_tables_on` (the public `seen_body_copy` table, row-level security `viewer = :sender`, in place of the motion views, `seen_bodies` or both motion tiers; the motion cue table stays with the tiers) and `characters_table_on` (the mirror `seen_character_copy` in place of `seen_characters`, which is the set's first query either way). With both table laws off (their shipped values until dev-box flips them) the set is the frame-views one plus `seen_characters`, so the client's queries are still main's. Both table laws are value-only delivery laws (`Applied::delivery`), so a `law_override` row switches the set like the frame laws. A switch into a table waits, beside the old set, until the table holds my scene (`tables_hold`: a viewer's copies move into it whole at its next frame, the views hold them meanwhile); a switch out of one (the kill switch empties the table in one tick) keeps the table's rows for the reads until the views are in (`Copies::leaving_*`, and `law_row_off`: a delete that arrives after the law's row says `false` is not taken). A law change that changes the set subscribes the new set beside the old, drops the old once the new one is applied, then moves the reads to it and clears the overlays; the client logs `perception: subscribing the … set (N queries; tables: motion M characters C; …)` and `perception: on the … set after N ms (tables: motion M characters C; … others; … were in the old set, missing now […]; K characters, missing now […])`. A reconnect subscribes the set afresh. Both laws are on in the shipped script (`cue_transport_on` since frame-views' acceptance), so a fresh world with no law override takes the tiered set with cues; a script that does not compile here, with no law read before it, takes the rules' defaults (`net::delivery_fallback`, both on: the tiered set), and a later one that fails keeps the last values read. Once the base is applied, the gaze owner view `my_senses_v_2` is a third subscription of its own (since gaze, 2026-11-19: one row, the player's applied band and senses; `Net::update_gaze` sends `human_gaze` from the zoom target), kept in every law state; a disconnect drops it with the perception set. One macro in `net.rs` (`perception_streams!`) pairs each stream's SQL names (untiered, near, far, cue) with its SDK accessors. Only the player's own connection subscribes; the facing switch's admin link (`facing.rs`) calls `set_world_law` and subscribes nothing. The views follow the character on the authority, so walking changes none of them. A tile world also subscribes `terrain_chunk` whole. Since experience-incremental (2026-11-22) my lines are in the perception set too, not the base: `my_experience`, or the public `experience_copy` table while `lines_table_on` is on (shipped on; the switch waits for the copies, `PlayerConnection::tables_hold`), read through `net::my_lines` ([perception.md](perception.md#lines-as-rows-experience-incremental)). Since heed-client (2026-11-26) a seventh choice, `Feed::throng` (bit 6 of the set's key): while `heed_on` and `heed_players` are both on (both off as shipped), `SELECT * FROM seen_throng` is added after the rest (row-level security `viewer = :sender`; nothing replaced, nothing to wait for), switched make-before-break like the others; read through `net::throng` only while the set in place has it. With either law off the set, its key and its log lines are exactly as before heed (`net::cue_tests::heed_off_leaves_every_set_as_it_was_and_on_adds_only_the_throng`); the log adds `rules: heed for players true|false` when it changes and ` throng true` to the set's tables while on. The client sends `human_heed` (pins and focus) only then. [verify-ui heed.md](../../verify-ui/features/heed.md).
  3. On a land world, two chunk windows of public world data, each moved by subscribing the new one before dropping the old one:
     - near, re-centred after 2 chunks: `terrain_chunk`, and since 2026-11-10 `resource_node` and `structure` (what F acts on; drawn by `world::things` except buildings, gates and trees, which the island draws itself), within ±3 chunks;
     - far, re-centred after 5 chunks: `lot` within ±11 chunks.
- Since 2026-11-10 the game connects with `with_confirmed_reads(false)`, sends what its input systems called in the same frame (`net::flush` after the inputs), and feeds the display clock only from body rows whose segment changed; it draws its own body at the display time plus `ServerClock::lead` (docs/LATENCY.md, steps 1–3). Every 10 s it logs `clock: input→drawn mine […] old clock […]; behind newest […] old feed […]; resyncs …`, the second of each pair from a shadow clock fed as before.
- `seen_bodies` and `my_body` rows are `Moving` (64 B: the travel segment, no path, chunk or kind, and since `look-2` the facing offset `face_off`, `face_turn`, `face_turn_s`). `net::body_of` rebuilds a `Body` for the drawing code: the kind from the creature's character row (`net::find_character`), an empty path, the chunk from `living_rules::map::chunk_of`, the facing fields as they come. `net::find_motion`, `find_fighter`, `find_doing`, `bodies` and `fighters` read the own row (`my_*`) and the others' together, so the drawing code does not tell them apart: on the untiered set a creature's row is its view's, as on main; on the tiered set it is in either tier, and over it a per-creature overlay from its stream's last cue (`Moving`, `Option<Fighter>`, `Option<Doing>`; `None` hides the tier row). A cue is taken only while the creature's body is in either motion tier; any insert, update or delete of that creature in the stream's tiers clears its overlay, a reconnect starts with empty overlays, and the world's `cue_transport_on` law off (read from the compiled `skills` script with the `law_override` rows laid over it, by `net::perception_law`) clears all and takes no cue. On a set with the motion table the others' rows are `seen_body_copy` rows: no key, so the client indexes them by `body` (`Copies::bodies`), a change comes as the new row's insert then the old one's delete (the SDK fires inserts first), `net::moving_of` makes the `Moving`, and a copy row's change ends that creature's motion cue as a tier row's does. Every read of characters goes through `net::characters`, `find_character` and `character_count`, which take `seen_characters` or the mirror (indexed by creature, `row.id`, not by the projected row's id). The display clock is fed from `my_body`, `seen_bodies`, both motion tiers, `seen_body_copy` (a new row of a creature already held whose `t_ms` moved) and `seen_body_cue`. `LIVING_GAME_SEEN_LOG=<file>` writes every frame's reads (the set in place, each other's id and segment `t_ms`, the overlays' sizes, since law-override-client the wall clock `wall_ms`, and since battle-views-client the tables read, `tables`, and the characters' ids, `characters`) as one JSON line, for checking a switch frame by frame.
- It regenerates the land from the `land` row and compares the three digests (`living/game/src/live.rs`, `land` and `regenerate`). It logs `digests match` or `DIGESTS DIFFER`.
- It joins with `join`. The newcomer arrives at `land.arrive_x/arrive_y`, and the client moves only through `human_move` and `human_act` (`goto`). `find_me` reads `my_characters` (alive, not AI).
- It draws buildings from `lot` rows, its own body from `my_body` and every body in `seen_bodies`: what the authority says the character perceives, within sight and with a clear sight line. A death takes the body out of `seen_bodies`; the corpse stays drawn from the death's `my_combat` row.
- What it shows of others is the projection (`seen_characters`): the `label` (the name when the character knows it, else `a stranger`, `a wolf`, …) on nameplates, speech bubbles, the log, the target panel and the death screen; build and dress from `folk` and `style`; health as the `seen_fighters` band, or exactly (`hp`/`max_hp`) while an appraisal holds, with a small `hp / max` under the nameplate (`ui/live.rs`, `ui/overhead.rs`). The death screen names the killer and witnesses by the labels the character last perceived, not from `character.cause`.
- The HUD shows vitals (`my_vitals`), heard speech (my lines: `net::my_lines`, from `my_experience` or `experience_copy`), death and rejoin (`living/game/src/ui/live.rs`).
- Wolves and deer are their rigged files (`bodies::spawn_beast`), played by `anim.rs`; a deer taking flight from standing plays `startle` first (`live.rs`, `STARTLE`).
- The camera frames a fight the character is in, a conversation or a gesture exchange (`camera.rs`, `Context`); turning the view dismisses it.
- Verbs (`living/game/src/verbs.rs`, `ui/verbs.rs`, docs/GAME_BRIEF.md "Verbs"): F acts on what is under the cursor or within 3 m, C on myself, I and K toggle the pack and know-how panels. The options are the catalog's and the installed script's skills whose `<skill>_check` passes on what the character knows; every act is a `human_act` (or a `human_say` for asking to be taught), and outcomes are read from `my_experience` rows of kind `act`. The log line `rules: skill script revision N compiled (M skills, K law overrides)` shows what the client found (and `rules: law overrides laid over in place …` a value-only edit); `verbs: <label> → <node>` each act sent; `live script: act … offered|not offered by the rules as this client knows them` what a scripted act would have been offered.
- The session record (`living/game/src/record.rs`, `record_frames.rs`, docs/PLAY_REPORT.md, since 2026-11-11), off unless `LIVING_GAME_RECORD=<dir>`: the session's frames as drawn, HUD included (`stills/<unix ms>.jpg`, `LIVING_GAME_RECORD_FPS` a second, default 10, `LIVING_GAME_RECORD_WIDTH` px wide, default 960; a render system after the UI pass draws a small copy of the frame and only that is read back; `LIVING_GAME_RECORD_FPS=0` takes stills every `LIVING_GAME_RECORD_EVERY` s and at events instead), `state.jsonl` (4 Hz: me, camera, the HUD's people, bubbles, chat, target, frame time, `rec_main_us`), `events.jsonl` (presses as the game reads them, lines sent, every reducer call with the authority's answer, hooked in `Net::on_reply`) and `captures.csv` (each frame's request and arrival time, worker time, size). The log says `record: writing frames, state and events to <dir> (N frames a second, W px wide)`. It reads the client's state only.
- Town life (`living/game/src/town.rs`): `doing.code` from `seen_doing` is named through `act_card` and drawn as a clip on the standing body (work, gather, eat, play, sitting, wave, nod; appraise plays `idle_look`); a sleeping person, or one resting whose `doing` row says `indoors` (the authority decides it from the home it no longer sends), is hidden; animals asleep or resting stay drawn. A standing body's facing follows its own segment (`heading` + `turn` × elapsed, up to `turn_s`), so turns at zero speed turn in place. Since `look-2` the rows (`Moving`) also carry the facing offset (`face_off`, `face_turn`, `face_turn_s`) that a held look turns; the client does not draw it yet (docs/PERCEPTION.md, "The player's look"). Rain follows the `weather` row. The keys G, B and V send `human_act` wave, nod and appraise ([verify-player gestures](../../verify-player/features/gestures.md), [perception](../../verify-player/features/perception.md)); appraise goes to any creature within 6 m, people or animals.

## How to get to it (user POV)

A player starts the game client against a server that hosts a land seed (`LIVING_SERVER`, `LIVING_DB`). The client connects, joins, and shows the island around the arrival point.

## Driving it

### The real client, headless

Launch a land world with the shared harness (`$V launch --run client-<name> --seed island`, then `$V doctor`), and build the game with `cargo build --release --manifest-path living/Cargo.toml -p living-game` in a private `CARGO_TARGET_DIR` (other sessions overwrite `living/target`). `LIVING_GAME_LIVE=<dir>` runs a script with no window and writes photographs to `<dir>`. `LIVING_GAME_LIVE_PLAN` holds `;`-separated steps, documented on `Script` in `live.rs`:

```bash
LIVING_SERVER=http://127.0.0.1:3300 LIVING_DB=verify-$R LIVING_GAME_TOKEN=.local/living/verify/$R/game.token \
LIVING_GAME_LIVE=.local/living/verify/$R/shots \
LIVING_GAME_LIVE_PLAN="ready;wait:3;shot:join;goto:416,250;wait:50;shot:plaza;say:Good morning!;wait:1;shot:say;quit" \
"$CARGO_TARGET_DIR"/release/living-game > .local/living/verify/$R/game.log 2>&1
```

Use a fresh `LIVING_GAME_TOKEN` path for each run. A reused token is an identity whose character may still be alive, so `join` is not sent. In the log, check these lines:

- `world kind: Land`;
- `land: regenerated in … s; digests match: tiles …, heights …, layout …`;
- `playing character #N`;
- every 10 s, `live: cache body … character … doing … act_card … weather dry|rain|none lot … terrain_chunk … (N tiles edited) …; drawn … characters, … lots; window moves …; digests …; cue overlays (M, F, D)` (the overlays' sizes per stream; `act_card` 18 and `weather` `dry` or `rain` on the island seed). The `body`, `character` and `doing` counts are the reads' rows (`my_body` + the others' motion rows of the set in place, `net::motion_count`; the characters it reads, `net::character_count`; `my_doing` + both `seen_doing` tiers) and `experience` is `my_experience`: what is in sight, so `body` equals `character` and is small away from crowds (1 alone at the arrival, 13–18 in a town square).

Script steps for verbs (since 2026-11-10): `act:SKILL[:ITEM][@AIM]` (AIM `nearest:KIND`, `id:N`, `self`, or nothing for F's current aim; sent whether or not the rules offered it, so a refusal can be driven), `menu:f[@AIM]|c|close|N` (open F's list or my own, close it, pick row N), `words:TEXT` (the text box an act opened), `panel:inventory|know-how[:SKILL]|none`. The proof driver of the verbs run is in the evidence (`drive_verbs.py`): it runs a private copy of the binary, sets scenes with admin reducers at `sync:` points (`grant_know_how`, `grant_items`, `set_behavior`, `place_near`) and snapshots the character's `inventory`, `know_how` and `experience` as the owner before and after.

Script steps for input (since 2026-11-10): `key:NAME:down|up|tap` and `mouse:left|right|middle:down|up` press and release a key or button as the window reports it, so every input system reads them that frame (holding E raises the guard, `key:KeyE:up` lowers it); `chat:open|close` opens or closes the text box. The feet log (`LIVING_GAME_FEET`) also records `mine_ms` (the authority time my body is drawn at), `seg` (my newest segment's `t_ms`, `next_ms` and speed), `action` (the one-shot asked of my body) and `eye` (the camera's position and pitch); `living/tools/root_steps.py` counts stalls and surges in my drawn motion from it. A connected frame runs in named phases (`living/game/src/phase.rs`: Net, Mirror, Input, Flush, Present, Camera). Offline the client draws no bodies and shows a notice; a TCP proxy that closes its connections on request (as `drive.py`'s `DropProxy` does) drives that.

Script steps for town life: `gesture:wave|nod|appraise[:ID]` (the G, B and V keys' path) and `sync:NAME` (waits for `<dir>/NAME.go`, so an outside driver can set a scene with admin reducers first; a number in the file sets the view's yaw). Since 2026-11-09 also `hold:DEG[:run]` (walk or run toward a heading until the next step) and `stop`, used by the animation probes.

To check the session record, add `LIVING_GAME_RECORD=.local/living/verify/$R/rec` to the command above: `rec/stills/` fills with JPEGs whose names are unix ms, ten a second (compare one with a `shot:` taken at the same moment: same picture, HUD included), `rec/events.jsonl` has a `call` row per reducer sent (a `refused` row with the authority's reason for a refusal), and `living/tools/play_report.py --db verify-$R --run $R --logs <dir of game.log renamed client.log> --capture .local/living/verify/$R/rec --out <dir>` draws them.

`island perf` lines report frame times every 2 s. They are capped at 60 Hz unless `LIVING_GAME_FPS_CAP=0`. They describe the machine and its load; they are not protocol evidence.

To photograph what the projection shows (a stranger's label until they say their name, an appraisal's exact health and its end, someone behind a wall not drawn), set the scene with admin `set_behavior` (a resident's graph `{"seq": [{"say": {"text": "Well met. I'm NAME.", "to": {"id": ME}}}, {"wait": 900}]}`; `{"wait": 900}` holds a resident still) and `place_at`, then photograph from the script. Read the game's own views beside each photograph as the game's identity: its token is the `LIVING_GAME_TOKEN` file, sent to `/v1/database/verify-$R/sql` (`verify.py`'s `http` helper) with `SELECT * FROM seen_characters`. A wave at a resident frozen this way gets no answer, so its nameplate does not show; the bubble and the log carry the label.

To exercise speech, death and rejoin, combine the script with the harness. `$V call … place_near` puts the run's harness player beside the game's character, and `$V player … say … --to <id>` makes it speak. The client shows a bubble for about `3.5 + 0.06 × characters` seconds (`ui/model.rs`, `bubble_life`), so photograph within that time. `$V call … kill '[<id>, "cause"]' --as-admin` kills the character. The script's `dead`, `rejoin` and `joined` steps then drive the death screen and its "Arrive as a new stranger" button. `place_near` and `kill` are admin scene setup; name them in the report.

### Each query through the probe

`drive.py` sends the client's exact queries. The run name must start with `client-`. Chunk ids are `(cy << 16) | cx`:

```bash
D=.agents/skills/verify-client/scripts/drive.py
ranges() { local col=$1 q=""; for cy in $(seq $4 $5); do q="$q${q:+ OR }($col >= $(( (cy<<16) + $2 )) AND $col <= $(( (cy<<16) + $3 )))"; done; echo "$q"; }
$V player --run $R join ProbeJoin
$D --run $R --as-player --save mine --seconds 2 --query "SELECT * FROM my_characters"
$D --run $R --as-player --save seen --seconds 30 --query "SELECT * FROM seen_bodies"
$D --run $R --as-player --save seenc --seconds 30 --query "SELECT * FROM seen_characters"
$D --run $R --as-player --save doing --seconds 30 --query "SELECT * FROM seen_doing"
$D --run $R --save terrain --seconds 3 --query "SELECT * FROM terrain_chunk WHERE $(ranges id 23 29 12 18)"
$D --run $R --save lots --seconds 3 --query "SELECT * FROM lot WHERE $(ranges chunk 15 37 4 26)"
$D --run $R --save acts --seconds 2 --query "SELECT * FROM act_card"
$D --run $R --save weather --seconds 2 --query "SELECT * FROM weather"
$D --run $R --as-player --save body-refused --seconds 2 --query "SELECT * FROM body"   # refused in a scoped build
```

`my_characters` must return exactly the harness player's character. `my_body` must return exactly its body, and `seen_bodies` must not hold it. `seen_bodies` rows carry the 11 `Motion` columns; `seen_characters` the projection (`label`, `hp` -1 except for the player's own character or while an appraisal holds); `seen_doing` at most one row per perceived body. The perception checks of the fixed suite ([perception.md](perception.md)) prove what is in and out of sight.

### Volume

Bytes per query come from the server's `spacetime_num_bytes_sent_to_clients_total{db=<database identity>}`, split by `txn_type`:

- `Subscribe`: initial rows;
- `Unsubscribe`: rows dropped when a window moves;
- `Update`: live changes.

`spacetime_active_queries{database_identity=…}` counts the live queries. While one game client walks, it must stay flat: 26 on a land world since 2026-11-10 (`scale-1`: 3 static, the 19 perception, own-state and rules queries, the near window's 3 and the far window's 1), and for a moment up to 29 while the near window moves (the new one is subscribed before the old one is dropped). Measured on 2026-11-10 before the own-row views (23 then): 0 before the client connected, a flat 23 sampled every 1.5 s while it ran through 3 window moves (the brief overlap was not caught), 0 after it left. It was 20 before the verbs, and 21 before the perception views (6 base, 6 by id, 5 in the near window, 1 far). If it grows, a moved window was never dropped. The database identity is `GET /v1/database/<name>` → `database_identity`. Sample with nothing else connected, or each client's bytes count toward the same total.

## Gotchas

- The views are per sender: an anonymous probe receives empty `seen_*` and `my_*` results, and the player's must use `--as-player`.
- Subscription SQL in 2.14.1 has no `IN`.
- The client draws any body only after its character row arrives (folk, stage, dress, and the kind itself). Before battle-views-client only people waited; since `seen_characters` left the base set, my own body arrives a round trip before the characters, and a body drawn without its kind would not be redrawn.
- Body rows are the live cost. `seen_bodies` sends the 64 B `Moving` row of each body in sight on each steering change (52 B `Motion` before `look-2`), and a view refresh re-sends the viewer's rows that changed. `spacetime_num_bytes_sent_to_clients_total` counts a shared query's bytes once however many clients hold it (docs/PERCEPTION.md), so measure one client's bytes with a proxy (living/tools/perception_bench.py's `Proxy`).
- A failed act (for example `build wall` without masonry) is refused in the actor's `my_experience` rows, not by the reducer's HTTP status.
- `character.cause` on my own `my_characters` row carries the killer's real name (authority text); the death screen does not show it, but the row reaches the client.

### Tile classes

Since drop-1 and eye-2 (2026-11-11) the hosted tiles carry two classes that block the foot and not the eye: `drop` (8, between ground levels) and `low` (9, what is low or open at eye height: a cart, an open stall, a well, a building's overhang; docs/ISLAND_AUTHORITY.md "Sight through what is open at eye height"). A client sees them as tile bytes in `terrain_chunk` and must get exactly the land the rules host. Subscribe every chunk through the probe on a land world and count the classes:

```bash
$V launch --run $R --seed island && $V doctor --run $R
$D --run $R --save terrain-all --seconds 3 --query "SELECT * FROM terrain_chunk"
.agents/skills/verify-client/scripts/tile_classes.py .local/living/verify/$R/terrain-all.jsonl --expect 8=DROPS --expect 9=LOWS
```

`DROPS` and `LOWS` are the rules' own counts for the build's land, the last line of `cargo run --release -p living-rules --example sight_census -- living/seeds/island.json` (`land: N low tiles, M drop tiles`; on 2026-11-11 with eye-2, 9,153 and 4,116). The script writes `terrain-all-classes.json` and exits 1 on a difference or an unknown class. The island's 16,384 chunks are about 4.3 MB in one initial update.
