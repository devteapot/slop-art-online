# Live world-law reinstall

## Recommendation

Use a value-only path for laws with known dependencies, beginning with dev-box’s delivery switches. Keep full source installation for Rhai changes and unknown dependencies. Consider external preparation for expensive edits after the value-only path is in place.

One confirmation on Spark: changing `fire_warmth` on a ticking island scratch world took **963 ms** inside the reducer, including **819 ms** in `install.validate`. The build used SpacetimeDB 2.14.1 and source at `4816ee6144c26a3b347de311645b465cd91954bf`, with temporary profiling spans. No players, observer subscriptions or model calls were active. The scratch logs and timing patch are in `~/slop-evidence/law-reinstall-2026-11-19.tar.zst`. [Install path](../living/authority/src/lib.rs#L137).

## Option 1 — Incremental value changes

The private `world_law` table holds name-keyed JSON overrides. Seed defaults and Rhai overlays define the law names and default values. The reducer checks kind, upserts the override, regenerates the `world_law_values()` suffix of the public `script` source, and calls `install_source` in the same transaction. On success it inserts `law_change` and a chronicle entry. The installed Rhai engine registers `law(name)` as a dynamic lookup in its in-memory `Tables.laws` map. The AST naturally supports a new value through that lookup. A fast path can supply the merged map from committed database rows when the law revision changes. A per-Rhai-call database lookup would add overhead to hot evaluation and couple shared rules to the authority. Direct Rhai calls to `laws()` still return the script's own map, as they do today. Some skill prose reads that map. Preserve that behavior unless changing it is a separate design decision. [Reducer](../living/authority/src/lib.rs#L212), [install](../living/authority/src/lib.rs#L137), [tables](../living/authority/src/tables.rs#L234), [Rhai binding](../living/rules/src/script.rs#L997), [merge and type checks](../living/rules/src/script.rs#L2835), [source suffix](../living/rules/src/script.rs#L3216), [example skill prose](../living/scripts/skills.rhai#L2420).

`Scripts::validate` walks field plans and runs sample probes against an engine sharing the merged law map. Static field plans, signatures and source checks can be reused for the same AST and engine configuration. Runtime probes check outputs, shape, operation budgets and cross-contracts. Their inputs can also depend on derived specs, table domains and speech reach or gap even when the function under test does not read the law itself. For example a changed speech spec changes the refusal cases the validator constructs. Cache successful probes by the source/engine/seed context and the effective inputs they depend on. Dependency discovery must cover transitive helpers, overlays, potential branches and dynamic lookup keys. Recording just the calls made by the old value misses paths newly taken with the candidate value. Conservatively fall back to full validation for unclassified dependencies. There is no persistent per-law proof cache today. [Validation dispatch and field plans](../living/rules/src/script/check.rs#L164), [speech test cases](../living/rules/src/script/check.rs#L208), [skill probes](../living/rules/src/script/check.rs#L398).

The current revision invalidates the compiled script and the typed law snapshot immediately. Hot caches and warming indexes refresh lazily. The appearance pass eagerly brings the new runtime into the transaction and makes rollback safety material. The in-memory caches must be disposable. An aborted candidate must never be visible as committed state, even if its revision number is reused. [Invalidation and rollback comment](../living/authority/src/common.rs#L278), [script reload](../living/authority/src/common.rs#L517).

### Commit and cache behavior

Split value updates from source installs. Start with a narrow set of demonstrably scalar-only laws and grow the set by adding dependency checks. Use separate source and law revisions. Keep the AST and static analysis for unchanged source. Stage the candidate effective map, type/range-check it, run affected value-dependent checks and publish the indexed override, revision and audit together. Refresh only affected law-driven state and publish the resulting card or policy deltas. Keep the existing full install path for source changes and unclassified values. Compare effective values before doing expensive work. Decide explicitly whether same-value requests still create audit events.

An ordinary value-only edit with no probes, bounded prose refresh and a warm script should target **under 5 ms of reducer time** on Spark. This is an engineering estimate. The measured law and audit spans total well under 1 ms and the 2+ s validator and duplicate constructor can both be skipped for that class. Budget **about 15–20 ms of extra work** for Cullet cover changes if the current lazy full-map refresh is retained. Keeping terrain and gates resident and rebuilding or staging only the cover mask would remove the rest of the full map reload. Gaze constructor sample work is sub-millisecond on these builds. Include mapped sense checks and owner revocations in its budget, and benchmark it separately with active owner subscriptions.

Keep the authoritative overrides and audit private. The game and mind service currently use the public script row to compile the world they see, so a value-only change needs a compatible client delivery path. For upgraded clients, consider a compact versioned effective-values projection for the laws already exposed in that source. Publish it transactionally alongside affected public cards, and have clients attach the matching values to their cached script during initial subscription, updates and reconnect. Preserve stable presentation codes. Define a transition for clients using the old source suffix. Ordinary edits should touch one indexed override, one revision and the audit and changed projection rows. The finite name-keyed tables scale with defined laws. The append-only audit grows with admin changes, and should retain its history under the project's evidence policy. Cover-policy subscribers receive a single changed policy row. Gaze projections are owner-scoped. World-scale reads should be confined to actual world-scale effects such as a cover rebuild, and no ordinary scalar edit should scan the character or appearance tables. [Game subscription](../living/game/src/net.rs#L110), [game compiler](../living/game/src/verbs.rs#L136), [mind subscription](../living/mind/src/main.rs#L193), [SpacetimeDB indexes](https://spacetimedb.com/docs/tables/indexes/), [subscriptions](https://spacetimedb.com/docs/clients/subscriptions/).

## Option 2 — External preparation on SpacetimeDB 2.14.1

Reducers run in one atomic transaction. Procedures can open and close separate transactions with `with_tx` or `try_with_tx`. Each callback holds the transaction during its work and can retry, so it is the wrong place for expensive preparation. The version-pinned Rust WASM host puts synchronous reducers and asynchronous procedures on the **same single-thread executor**. Procedure instances are pooled, and yielded host I/O can let other jobs run, but a straight-line Rhai compile or probe loop still blocks the worker even outside `with_tx`. A schedule table can defer the commit or trigger a procedure to call an external worker. In 2.14.1 the scheduled reducer dispatches to the same main instance path as an ordinary reducer, so scheduling the validation loop merely moves the pause to a later tick. The bound SDK and server image in this run are both 2.14.1. [Reducer docs](https://spacetimedb.com/docs/functions/reducers/), [procedure docs](https://spacetimedb.com/docs/functions/procedures/), [schedule tables](https://spacetimedb.com/docs/tables/schedule-tables/), [pinned scheduled dispatch](https://github.com/clockworklabs/SpacetimeDB/blob/v2.14.1/crates/core/src/host/module_host.rs#L3507-L3518), [pinned WASM executor](https://github.com/clockworklabs/SpacetimeDB/blob/v2.14.1/crates/core/src/host/module_host.rs#L496-L506), [procedure dispatch](https://github.com/clockworklabs/SpacetimeDB/blob/v2.14.1/crates/core/src/host/module_host.rs#L2116-L2152), [Rust transaction API](https://github.com/clockworklabs/SpacetimeDB/blob/v2.14.1/crates/bindings/src/lib.rs#L1640-L1706).

A procedure can compile Rhai outside a transaction and retain the result inside that procedure call. It cannot hand a live `Scripts` object to the main reducer instance. The object contains the engine, AST and instance-local state, and the pooled procedure and reducer instances have distinct memory. Returning source plus a validation result only removes validation from activation. The authority still has to compile that source before rules can run. The measured island constructor was about 69 ms, so this approach can still skip multiple 60 Hz ticks even if activation does one constructor pass and skips the duplicate reload.

If expensive changes need to stay interactive, a trusted native worker can prepare them using the same rules crate, pinned engine and candidate world inputs. It could run beside the mind service with no inference call and a narrow authority to submit prepared results. An admin request records the expected source revision, law revision and inputs. The worker returns a versioned candidate containing source and effective values, evidence of successful validation, and portable typed outputs where applicable. For example, a cover candidate can contain a mask built against a particular geometry revision. There is no existing portable compiled Rhai representation in the project. Eliminating first-use compilation for source changes would require an explicit portable executable format or another execution strategy.

Store the candidate under a private immutable ID. In a short transaction the activation reducer checks the caller, candidate identity, source and input fingerprints and expected revisions, then changes the active pointer, public projection and audit together. For variant data staged over several transactions, readers follow only the active revision. A stale or duplicate completion is rejected or recognized idempotently, and a failed job leaves the current revision live. Any large decode, unbounded row copy or client projection rebuild at activation can still stall ticks. Measure activation and the first tick separately.

## Dev-box integration

After frame-views merges, use `cue_transport_on` and `near_tier_on` as the first members of the delivery-only dependency class. Let those consumers read the committed row value or its transaction-scoped typed snapshot. Give each switch its existing default for worlds with no override. Keep a single source of truth for each value and preserve the existing authorization and audit semantics. If dev-box lands a dedicated typed row or setter, keep it as a compatibility entry point into the common write path or migrate its value into the canonical override atomically. Avoid dual writes that leave either reader able to see an older value. Test each toggle with active frame-view subscribers. The two switches should neither advance the source revision nor refresh Rhai or spatial caches unless their merged implementation introduces such a dependency. The handoff is a design contract for the dev-box and Opus implementations.

## Acceptance tests

- Toggle a delivery-only flag while the tick advances. Assert zero Rhai compiles, full validation runs, `script` row writes and unrelated cache refreshes. Repeat with an old world missing the override and with a connected frame-view client.
- Compare targeted validation with a full install for shipped and overlay scripts. Include a helper that makes a dynamic law lookup, a change that takes a different branch, and a law that changes a derived spec or a speech-check fixture. These cases must use the affected dependency set or the fallback path.
- Switch gaze off and on with active observers. Check owner-view revocation and sweep-based refresh. Change a cover policy and verify rays against the expected geometry, one rebuild for that revision and no rebuild for an unrelated value. Check that unrelated values leave appearance scheduling and presentation codes alone.
- Reject an invalid candidate and force rollback after writes have begun. Confirm the next tick and reducer see the old law, audit, dependent caches and client projection. Retry, restart and reconnect. In the external path, race a completion against a second edit, source install or geometry change, and verify that only the matching candidate can activate.
- Profile the commit and following tick under representative load. Measure the ordinary **under 5 ms** reducer target and the separate cover-map budget, including subscription fanout. The proposed path and the frame-view integration were not built or timed here.
