# Explicit owner snapshots

Owner exports can use `sim_owned_run_ids()` and `sim_export_owned_run(run)` instead of the `sim_run` compatibility view. These procedures return the same complete, self-contained World to its authenticated run owner. Missing and foreign runs return the same unavailable error. A participant or observer grant does not confer ownership; even the database operator cannot use this procedure to export another identity's run.

Inventory reads the private owner index and returns sorted run IDs. Export verifies ownership before constructing its blob reader, hydrates a coherent World inside one transaction, then serializes the owned result after the transaction finishes. The adapter cannot intern data. Export does not advance the world, change controls, create participant observations, or return arena references. Canonical content and scope validation remain mandatory. The pinned SpacetimeDB 2.1.0 module SDK requires its `unstable` feature for procedures. The dedicated scale service runs server 2.1.0; publication and control use CLI 2.7.1, as recorded in its [service manifest](../output/society-lab/reality-m7-build-verification/dedicated-scale-service-3102/SERVICE_READY.json).

The CLI/HTTP return is an untyped SATS result: `[0, payload]` on success and `[1, error]` on application failure. An HTTP 200 or successful CLI exit does not establish application success. The shared Python and Rust parsers validate the result shape, reject malformed responses, and preserve the exact inner World JSON. Callers retain their existing transport deadlines. There is no retry or fallback to SQL.

The host selects `SAO_OWNER_SNAPSHOT_API=sql|procedure`; the default is `sql` for compatibility. The pilot's `--owner-snapshot-api` selects the same mode for host and supervisor and records it in evidence. A batch variant can set `owner_snapshot_api: "procedure"`. The standalone `sao-sim` runner records the mode in its manifest; missing historical fields mean SQL. The three-case authority diagnostic also keeps SQL as its default and requires explicit procedure selection for a changed comparison.

## Observer cost and experiment boundaries

A SQL projection such as `SELECT id FROM sim_run` can materialize the whole owner view. On the pinned server, that view may remain and refresh on relevant writes even without an active subscriber. The measured profile found a full owner World refresh after each of 144 participant requests. One-shot procedures avoid registering this retained view; each requested export still performs real loading, validation, allocation, serialization and transport work. The read transaction can still delay other work.

The original SQL-observer tests remain failed, including the Experience-batching candidate's 120 timely receipts out of 144. The new procedure condition is declared separately. It keeps the same 36-person seed, participant API, four rounds of 36 requests, ten-second receipt deadline, fixed sixty-second active window, ten-second pause requirement, zero retries and resource limits. Owner inventory and mandatory baseline/final exports remain at their original checkpoints. No new owner `sim_run` SQL query may occur before or during that measurement. Compatibility checks run in separate databases.

Before a model trial, require actual procedure ownership/error/parity/no-mutation checks, the separately declared participant access gate, exact authored-law/private-case/retained-read storage checks, and clean pause/revocation with passing resource evidence. The law fixture retains its SQL observer workload; optional procedure equality checks occur only after pause and the original final measurement boundary, before retained-read collection. The model host retains its existing export cadence with procedure mode selected explicitly. Earlier failures, changed observer lifecycle, process conditions and finite-run limitations remain in the evidence; a passing sample cannot establish sustained 20 Hz, arbitrary scale or autonomous law editing.
