# Persistent external MCP transport

The pilot can retain one external worker and one actor-scoped MCP child across scheduled responsibilities. Select it explicitly with `--external-mcp-mode persistent`, or set `external_mcp_mode: "persistent"` on a batch variant. The default remains `per_call`. This option changes connection lifetime; the pilot still schedules each behavior, communication and learning opportunity and counts failed attempts. The worker never creates extra turns, retries a request, repairs a proposal, restarts a dead MCP child or falls back to the older runtime.

The existing `participant_live_agent internal|external SESSION CONFIG ROLE OUTDIR` interface remains available. Persistent mode uses `participant_live_agent external-worker SESSION ACTOR_OUT_ROOT` with piped stdin/stdout and the `sao-external-worker-v1` JSONL protocol documented in [the example README](../server/bridge/examples/participant_live_agent/README.md). There is one in-flight job and no job queue. Every job has a strictly increasing positive ID, an absolute configuration path, one responsibility and a single output-directory name under the actor's audit root.

The first valid configured job starts the MCP process; later jobs reuse that same process and participant subscription. Each job obtains fresh discovery, tool contracts and `observe(after_cursor=0, limit=256)` state before forming the normal single-attempt provider request. Both external runtimes use the same payload function, grounded schema and controller-feedback behavior. Only the current observation and existing controller-feedback contract enter model context. Worker process IDs, connection diagnostics and prior response frames do not enter the request. Tool receipt errors retain the older runtime's distinction from the overall model result.

## Deadline boundaries

Persistent mode's **15-second MCP timeout covers the whole RPC: writing the request, flushing it and waiting for its response**. The legacy per-call client starts its 15-second response timeout **after** write and flush complete. The nominal number is unchanged, but the boundary is deliberately stricter for the persistent transport. The two timings must not be described as identical.

The authority-side participant behavior is unchanged: the initial scoped-state wait remains five seconds and a participant command receipt wait remains ten seconds. Provider configuration still requires one attempt and permits a deadline up to 300,000 milliseconds. The pilot's persistent job has a 315-second outer deadline that begins before lazy worker/MCP startup. A configured 15-second serial interval remains a delay after each scheduled responsibility completes; persistence does not shorten it or add calls.

A dedicated MCP reader retains incomplete frames independently of the waiting job. After a fully written request times out, it discards any later response for that retired ID and counts it locally. A subsequent scheduled job starts a new observation. An application error can also leave the transport reusable. A partially written or interrupted write, malformed frame, invalid response ID, EOF or cancelled job makes the transport unusable. Requests whose delivery may be unknown are never replayed.

## Optional external RPC admission

`--external-rpc-concurrency 8` (batch variant `external_rpc_concurrency: 8`) enables a run-local admission limit for persistent external `tools/call` RPCs. Zero is the default; positive values require persistent mode and must be at most 36. The pilot creates a private directory with distinct lock files and gives its path and count only to the external native workers. Each RPC opens and exclusively locks one fresh file handle, then releases it when that RPC returns, fails or is canceled. Process death also releases the native worker's lock.

The same fifteen-second RPC deadline starts before admission waiting and covers waiting, writing, flushing and response. Discovery and tool-list calls do not acquire permits. Model inference starts after the observation permit has been released, so this option does not cap model concurrency. Initial participant readiness and atomic receipt deadlines remain unchanged. These locks coordinate participating external workers in one run; they do not limit built-in clients or guarantee service-wide concurrency, particularly after a dispatched call times out.

An admission timeout before dispatch has no issued RPC ID or flush timestamp and records `delivery_unknown: false`. Sent requests retain their own delivery uncertainty. Native journals record configured count, slot, admission wait and outcome; they do not measure exact server execution intervals. Inherited admission variables are cleared by the pilot, and slots are never silently reused from an earlier pilot output.

## Cancellation and final capture

The supervisor sends `cancel` for an interrupted active job and `shutdown` when closing the worker. EOF, SIGINT and SIGTERM also request shutdown. The native worker retains available model reply or tool-receipt evidence, acknowledges the active job as interrupted, kills its MCP child and explicitly waits up to three seconds to reap it. On Linux, asynchronous Unix pipe descriptors let shutdown complete even while the supervisor keeps stdin open. Idle shutdown has no job acknowledgement.

The Python supervisor owns a separate process group per external worker. It sends shutdown, waits for its bounded grace, signals the entire owned group with SIGTERM and then SIGKILL, and finally reaps the leader. It preserves the leader's PID until group signalling is complete, including when an MCP descendant keeps a pipe open. A bounded reader-thread join records incomplete cleanup instead of waiting indefinitely on a buffered-stream lock. Workers are stopped in parallel at pilot shutdown; an unsuccessful cleanup remains a failure.

`--finalization-mode stopped_host` is a separate explicit option for fixed-population runs; its default remains `legacy`. After stopping model workers, it stops the owned host before final capture, requests and confirms pause, revokes every grant for that run (including an observer grant), confirms the run remains paused with no grants, and exports the final World once. It then captures audit events below that World's `next_event` and requires the exact contiguous range `1..next_event-1`. Each authority operation keeps the existing finite CLI deadline. There are no cleanup retries, extra ticks, replacement grants or operations on other runs. Host/process cleanup failure still triggers scoped pause and revocation where possible, but cannot produce an accepted final capture. Newcomer enrollment is not supported by this finalization mode.

## Evidence and limits

`worker-job.json` starts before MCP setup and records failures even when no participant context exists. `external.json` starts only after an actual observation and backend payload exist. The worker journal records the MCP PID, random process-instance identifier, process creation time, issued RPC IDs and discarded late-response count. Its per-job RPC entries identify method/tool, request ID, start and flush time, elapsed time, deadline and outcome. These transport IDs are not authority read-request IDs; `observe` does not return the latter. Any authority reconciliation must state its separate matching rule and reject ambiguity.

Offline checks cover exact legacy-payload parity across all responsibilities, split response frames across timeout boundaries, write cancellation, protocol rejection, early setup failures, actual worker/child reuse, application errors, fatal framing, provider cancellation, signals, process reaping and the pilot's real Python supervisor connected to the native worker through fake MCP and deterministic local HTTP fixtures. These checks perform no authority operations or model inference. They establish the transport contract for those cases. A representative live authority workload, changed browser-observer condition or model campaign is a separate measurement and does not repair earlier failed trials.
